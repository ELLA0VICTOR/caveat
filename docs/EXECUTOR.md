# Wallet-funded execution

The v2 executor is a shared, immutable guard for one verified Soroswap pool. It exposes `swap` and `add_liquidity`; it has no arbitrary calls, approvals, withdrawal administrator, or upgrades. The v1 account remains unchanged for owner recovery and its original verification record.

Every action binds the wallet owner, exact token/router/pair identities, maximum spending, minimum receipt, expiry, mandatory zero approvals, and a persistent per-owner nonce. The owner authorizes the invocation and its exact wallet-funding transfers. The executor funds the action inside that invocation and authorizes only the exact nested input transfers to the signed pair. It ignores router return claims, checks actual balances, refunds leftovers, and delivers the result to that same owner. It checks the final wallet deltas before advancing the nonce. A violation aborts the entire invocation, including funding and settlement; transaction fees remain outside the checks.

Input/output balances present in the executor before the action are treated as baselines. They cannot be spent by the adapter or returned to a later caller. Direct donations are unsupported and have no recovery API. There is no shared user deposit balance. Per-owner nonces use persistent storage with TTL extension, and validity is capped at one hour. Archived state must be restored rather than silently treating an existing nonce as a fresh account.

Liquidity uses the existing pool's reserves to calculate the exact two permitted transfers within the signed maximums. The minimum receipt is measured in the pair's ownership tokens, which are returned to the wallet. Empty pools are rejected. The quote estimates shares from reserves and total supply; fee-on liquidity dilution and pool changes can reduce the actual result, in which case the signed minimum can cause rejection.

The SDK must verify the deployed executor's bytecode/configuration, Soroswap router/factory/pair provenance, and exact SAC identities. The contract enforces its immutable route and token identities against all callers. Honest input/output/LP token balance reporting, uncompromised wallet authorization, and Soroban atomicity remain assumptions. The guard does not assess economic fairness, protect issuer freeze/clawback, or intercept transactions that bypass its two endpoints. Another app must explicitly integrate it; the separate example is an integration demonstration, not third-party adoption.

G-address wallets need a Stellar trustline to receive test USDC. This is one-time asset setup, not a deposit into Caveat. Pool shares are SEP-41 balances in the pair contract. Only Freighter signs user transactions; the SDK never accepts a secret key. A separate disposable test identity can deploy and verify public Testnet infrastructure without reading user credentials.
